# Database Schema Overview

## Foundation Schema

The first Flyway migration creates identity and RBAC foundations only:

- `users`
- `roles`
- `permissions`
- `user_roles`
- `role_permissions`
- `refresh_tokens`

## Identifier Strategy

All primary keys use UUID values generated by the application layer. Seeded role IDs are stable UUID constants so permission assignments can reference them in future migrations.

## Time Strategy

- Audit timestamps are stored as `TIMESTAMPTZ` and handled in UTC.
- User-facing scheduling rules should use `Asia/Ho_Chi_Minh` and be documented in appointment-specific ADRs before scheduling implementation.

## Scheduling and Appointment Integrity

- `doctor_schedules` and `doctor_schedule_exceptions` are scoped to an
  assigned `(doctor_id, branch_id)` pair.
- `appointments.branch_id` is nullable only for the legacy/local demo flow.
  A non-null branch must be assigned to the doctor.
- V9 normalizes schedule weekdays to ISO-8601 (`1 = Monday` through
  `7 = Sunday`) and adds the active appointment interval exclusion.
- V10 adds composite doctor/branch foreign keys for schedules, exceptions, and
  appointments, plus validation for `CUSTOM_HOURS` exception intervals.
- V10.4 rejects the reserved all-zero branch UUID and records expired or
  malformed pending holds as cancelled history before repair.
- V10.5 deterministically preserves active appointments over overlapping pending
  holds and cancels later conflicts before V11 adds the final active-slot
  constraints. It never deletes booking rows.
- V11 rebuilds the active-slot unique index and interval exclusion with a
  normalized branch key. A reserved zero UUID represents legacy `NULL` branch
  rows, so branchless rows remain exclusive with each other without colliding
  with explicitly branch-scoped appointments.
- V12 adds the typed CMS content and change-feed tables. V13 is an idempotent
  repair for legacy volumes that reached V12 before the scheduling constraints;
  use the documented `SPRING_FLYWAY_OUT_OF_ORDER=true` maintenance start only
  after a backup and database-history review.
- See [ADR-003](../adr/ADR-003-appointment-concurrency.md) for the slot API
  contract and concurrency strategy.

## Seed Roles

The foundation seeds only roles required by the near-term product scope:

- `PATIENT`
- `DOCTOR`
- `ADMIN`

Additional roles such as `STAFF` or `SUPER_ADMIN` require concrete use cases before migration.

## Large local fixture

`apps/backend/src/main/resources/db/seed/seed-large-data.sql` generates
fictional local data for pagination, search, and performance checks. It is
idempotent for the domain tables it owns and must run after the migration set.
The seed is intentionally not a production snapshot and contains no real
patient information.

The database package build copies the 15 SQL migrations into a PostgreSQL 16
image, executes them in Flyway version order, and then runs the large seed on a
fresh `PGDATA`. Because this standalone image does not maintain
`flyway_schema_history`, it must not replace the application-managed Compose
database for Spring Boot startup. Use the package for a ready-to-query fixture;
use [`infrastructure/docker-compose.yml`](../../infrastructure/docker-compose.yml)
for the normal Flyway lifecycle.
